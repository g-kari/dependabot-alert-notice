# Dormant atomic release storage

This is K293 stage 2: an internal Store API, not a running connector, restored
controller, scheduler, account/authentication feature, or live configuration.
Stage 1's pure [release candidate codec](security-enrichment-release-candidate.md)
continues to inspect syntax only. Store proof is a separate operation.

## Retained request and fresh write

`ReleaseSecurityEnrichmentOperation` accepts only the original leaf
`ReleaseRequest`: its retained reservation intent/root and complete terminal
AppendRequest/digest. There is no independent Attempt/Completion input and no
UUID, clock, failure, metadata or next cursor generated by this API.

Before SQL, pure inspection owns all nested input and checks the existing
bounded journal shape. The write transaction then verifies:

- Exact operation, non-authentication intent, request/source and generation.
- The complete stored reserved payload and legal journal history, at most five
  checkpoints, including the exact current nonpending returned head.
- For success, the retained full Completion against the historical receipt,
  manifest and every observation. For failure, the exact retained failure code
  and finish clock. Current Finding revisions and independent current common
  facts are not historical proof inputs.
- For no-run, a legal sequence-two returned branch, no Prepared value, no run
  UUID in either journal header or progress, and no business receipt. Existing
  legal no_targets/exhausted/invalid/error/canceled shapes are not fabricated
  failures or execution grants.

The transaction inserts the deterministic certificate and CAS-clears both
active IDs while retaining the generation. INSERT and CAS must each affect one
row; exact post-write proof is checked in the same transaction. Suppressed or
mutated writes cannot yield acknowledgement. Commit and a final original-context
check must succeed before acknowledgement is returned.

A released request is not a fresh write replay. Repeating Release is rejected.
A caller with an error retains the same full request and can only read its
proof; this API performs no automatic write retry, replacement UUID or takeover.

## Certificate storage and ordinary-DML immutability

Additive migration 006 creates one certificate table, with:

- An explicit NOT NULL operation primary key in a WITHOUT ROWID table.
- Unique intent and (connector, generation), plus FKs only to existing unique
  reservation identities and the checkpoint composite primary key. FKs do not
  replace full binding/history/business validation.
- The independent certificate version's twelve fields, canonical certificate
  JSON bounded at 4 KiB and its own SHA256. This certificate digest is neither
  the journal checkpoint digest, OriginalDigest of decoded parser input, nor a
  business refresh-success receipt.
- BEFORE INSERT collision rejection for every logical unique key, including
  finite TEXT/BLOB aliases, and unconditional UPDATE/DELETE rejection. Ordinary
  INSERT OR REPLACE and UPDATE OR REPLACE cannot delete an older certificate.
  Hidden rowid replacement is absent, without relying on recursive_triggers.

This protects ordinary DML only. It is not an authentication proof against DB
administrators, removed triggers, replaced schemas, or rolled-back backups.
Existing observation/history tables are not made SQL-immutable by this change.
The owned corruption tests deliberately bypass constraints/triggers to model
bad storage; no such bypass or repair API is exposed by the product.

Migration code runs in the existing migration transaction. Tests reconstruct
the previous schema in a synthetic owned file and check preservation of nonempty
legacy data and receipts. This is not an operational database application,
old-binary test, backup/restore drill or mixed-binary safety claim.

## Read-only proof and source consistency

`ReadSecurityEnrichmentRelease` accepts the same complete retained request.
One read-only transaction checks SQL scalar types/byte caps before payload
Scan, strict certificate codec/canonical bytes/recomputed SHA, stored root and
full legal history, and historical business evidence again. Only matched exposes
acknowledgement. It is historical storage proof, never current execution,
different-caller adoption or permission to fetch after restart.

Clean missing requires a fully proved still-active terminal binding, or a
completely unused request with no conflicting source/journal/business evidence.
Positive idle without a matching certificate is corruption, not retry/admission
permission. A certificate plus its exact same-generation source still active is
an impossible atomic-release mixture and is also corruption. A valid later
generation may coexist with an older historical release proof; such a read does
not regain the old active fence.

The private proof dependency order is raw bounded readers -> retained
root/history/business proof -> certificate-backed idle validation -> top-level
source checker/public API. No public reader, source-checker recursion, mutex
reentry or nested transaction is used to build historical proof.

Certificate selectors use indexed operation/intent/source-generation keys and
finite BLOB aliases. At most three canonical matches are materialized, with a
fourth rejected. Existing binding/header/history/200-target evidence limits are
reused. These are Go materialization bounds, not a global SQLite-work or
filesystem/power-loss guarantee.

## Coupled compatibility boundary

A certified positive idle source is accepted by the two-source validator only
after re-proving its historical business evidence. Thus releasing one of two
active sources does not invalidate the other source's existing generation,
journal head or business write/read path. Damaging an old receipt, manifest,
observation or expected failure prevents reads/admission from trusting its
certificate alone. Legitimate newer offline facts/Finding revisions remain
independent.

Next-generation admission is deliberately disabled: both Reserve and a new
read-only reservation candidate explicitly conflict on the target's positive
idle generation, including no-run histories without an ingest receipt. An
unadopted other source remains usable. A fully certified old reservation's
missing-active condition becomes stale conflict with zero acknowledgement;
uncertified missing active state remains unknown/corrupt.

Certificate-only adoption residue is checked by initial admission, source
validation and the common six-entry legacy guard using source aliases and
reservation/journal identities. A positive generation still blocks all six
legacy feed operation/receipt entrances after release. Independent offline
common-fact updates, legacy threat snapshots and nonfeed defaults are not an
exclusive source fence.

Stage 3 remains required before next Reserve: a finite per-source admission
budget with H+1 metadata overflow detection, contiguous generations and full
proof of every closed generation, processed sequentially. A certificate must
not replace historical observation proof. H is separate from the unchanged
16-record non-evict manual controller.

## Evidence scope and work still separate

The tests use owned SQLite, synthetic clocks/receipts/CVEs and existing fenced
APIs. The outer lost-return wrapper commits a real Store call and then returns
an artificial error; it does not inject ambiguity into the driver's Commit.
Contention tests establish at most one fresh acknowledgement and atomic pairs,
not guaranteed progress. Rejected/canceled/read-error paths expose zero
acknowledgement and do not repair, release or retry.

Local Go/SQL execution was prohibited for candidate preparation; runtime claims
must come from formal CI against the final immutable head. Further work remains
for next-generation admission, K294 controller restoration/private-unknown
resolution, terminal capacity/retention, and K286 operational backup/mixed-writer
checks. This slice changes no controller constructor, public DTO, 16-record
retention, main/config/UI/scheduler/default endpoint or live operation.
